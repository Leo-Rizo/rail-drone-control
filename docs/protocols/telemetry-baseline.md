# RAIL-F01 — Telemetry Baseline

This document defines a preliminary logical telemetry record for future implementation. It does not define serialization, framing, authentication, transport reliability, or command semantics.

## Preliminary data model

| Field | Preliminary type | Meaning / units | Notes |
|---|---|---|---|
| `timestamp_ms` | unsigned integer | Monotonic time since boot in milliseconds | Source clock and wrap handling TBD. |
| `system_state` | enum/string | `BOOT`, `SELF_TEST`, `DISARMED`, `ARMED`, `RUNNING`, `FAULT`, `EMERGENCY_STOP` | Defined in the safety state machine. |
| `control_mode` | enum/string | Active mode, or `NONE` while inactive | Modes TBD; do not assume closed-loop modes exist yet. |
| `altitude` | number or null | Estimated height in meters | Null/invalid when no valid estimate is available. Reference datum TBD. |
| `altitude_reference` | number or null | Height target in meters | Null when no target is active. |
| `angle` | number or null | Angular orientation in radians | Axis, sign, and wrap convention TBD; likely pitch-like rail-plane angle must be confirmed. |
| `angle_reference` | number or null | Angular target in radians | Null when no target is active. |
| `angular_velocity` | number or null | Angular rate in radians/second, if available | Axis/sign and IMU report mapping TBD. |
| `motor_1_command` | number, enum, or null | Requested command for propulsion channel 1 | Units/range/meaning depend on selected ESC protocol. This is command, not measured RPM/thrust. |
| `motor_2_command` | number, enum, or null | Requested command for propulsion channel 2 | Units/range/meaning depend on selected ESC protocol. |
| `battery_voltage` | number or null | Measured battery voltage in volts | Calibration, measurement range, and freshness TBD. |
| `imu_ok` | boolean | IMU considered valid and fresh | Should reflect health/freshness policy, not merely bus presence. |
| `tof_ok` | boolean | ToF considered valid and fresh | Should reflect health/freshness policy, not merely bus presence. |
| `upper_limit` | boolean or null | Upper switch active state | Null if unknown/invalid; electrical active polarity TBD. |
| `lower_limit` | boolean or null | Lower switch active state | Null if unknown/invalid; electrical active polarity TBD. |
| `gamepad_connected` | boolean | Whether the expected controller link is active | Connection alone does not indicate fresh/valid controls. |
| `fault_code` | enum/integer/string or null | Current/latched fault identifier | Code registry and clearing semantics TBD. |

The logical fields above are generated by the ESP32. The external dashboard consumes and displays them; it is not a source of truth for safety-critical state. Additional validity, sequence, freshness, and protocol-version fields may be needed when a transport is selected.

## Transport baseline

- **USB Serial:** Development and debug path. Direction may be bidirectional for local diagnostics/configuration, but any inbound command must be validated and constrained by local safety logic.
- **Wireless dashboard telemetry:** Wi-Fi is the provisional path; transport protocol, rate, encoding, security, and reconnection behavior are TBD.
- **Bluetooth gamepad:** Separate operator input path. It is not the dashboard telemetry transport.
- **Loss behavior:** Dashboard loss must not affect stabilization or safety ownership. Gamepad loss while operator input is required should cause an appropriate local fault or safe stop, according to the active mode.

## Open protocol decisions

Encoding, units/conventions for orientation, field validity conventions, fault registry, sampling/publication rates, message versioning, transport framing, authentication, and any accepted remote configuration commands remain TBD. No serialization or telemetry code is introduced by this baseline.
